# Outcome

Open a backend-free lab and manipulate one persistent card, with actions working independently, simultaneously, and while already animating.

## Design and constraints

Build fresh code in `packages/card-engine/` and new examples, not incremental changes to legacy engine files. Backward compatibility is out of scope. Read the full accepted requirements in parent specification #1; this slice adds only the behavior listed below. Keep app/lab labels and accessibility text English; localization may be added later. Use the same public interface in consumers and tests. Do not publish/deploy as part of implementation.

## Scope

- Create packages/card-engine/ and examples/card-engine-lab/ with their own runnable tooling. Build fresh modules; do not import or wrap the legacy engine or modify the old lab.
- Expose a small scene interface for desired snapshots, transactions, lifecycle results, and disposal. Define arbitrary zone IDs, named content faces plus faceUp/faceDown, and operation/channel ownership. Model selection/drag intents as sets/batches from the start.
- Render one card with title, image, flavour, and a concealed back in one simple zone. Offer stage-position movement, local rotation/tilt, uniform scale, and flipping around a stable pivot. The acceptance renderer is a true closed extruded rounded shape profile with two large face surfaces and continuous side geometry; the first profiles are rounded rectangle and shield. CSS fallback implementation is deferred to issue #16.
- Support an optional logical face cycle with one shared physical back; the default card remains one logical front plus that back.
- Drive simultaneous channels from a sampleable clock. Retarget from the current visible state without resetting unrelated channels. Include reduced motion and safe destroy.
- Support intermediate face angles, persistent in-place spinning with an explicit stop handle, and simultaneous X/Y flip axes through the Cardinal scene interface.

## Acceptance criteria

- [ ] Each action runs alone and move/rotate/scale/flip run together on the same shell; they can start or change mid-animation.
- [ ] Movement/scaling alone preserves internal layout and text wrapping. Text remains acceptable under depth/scale in actual browser recordings.
- [x] Final animated pose matches the committed resting pose in deterministic scene tests. Interruption and destroy produce no stale cleanup or unresolved operation handles.
- [ ] The renderer keeps a true physical cuboid mesh during oblique X/Y flips; geometry is owned by Cardinal rather than the lab.
- [x] The primary renderer is a true 3D beveled extruded shape profile with real thickness; CSS is never selected automatically.
- [ ] High-resolution front/back content remains readable and keeps canonical line breaks at 100%, 150%, and 200% scale during motion and at rest.
- [ ] Run deterministic channel tests plus Chromium/Firefox/WebKit smoke scenarios. Record reference device, card counts, frame timing and input-latency baselines; do not claim visual quality from unit tests alone.

## Runnable lab scenario

Move the card between two positions while rotating, scaling, and flipping; reverse it mid-flight; repeat with reduced motion.

## Dependencies

None. This is the first Ready slice.

Each issue delivers working behavior from public commands/project intent through state, layout, rendering, and a runnable consumer scenario. Add focused tests at that seam; preserve relevant independent animation channels. Complete the slice's acceptance checks before moving it to Review.

Current verification commands: `npm --prefix packages/card-engine test` (60 tests),
`npm run test:chrome` (15 element checks), and `npm run test:chrome:acceptance`
(9 motion checks plus input-latency and landing-delta measurements). The lab exposes
independent X and Y flip-angle sliders and the engine composes those rotations on
one persistent cuboid shell. The true-3D renderer work is planned in
`docs/plans/true-3d-renderer.md`; WebGL-only implementation is complete through
context-loss status reporting and recovery. Chrome visual and acceptance evidence
is recorded in `docs/verification/webgl-browser-evidence-2026-09-14.md`; the
Firefox/WebKit visual pass remains required before this slice can move to Review.
