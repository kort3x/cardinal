# Outcome

Deal several cards in a stagger, perform sequenced visual actions, and remove/re-add cards without blocking interaction.

## Design and constraints

Build fresh code in `packages/card-engine/` and new examples, not incremental changes to legacy engine files. Backward compatibility is out of scope. Read the full accepted requirements in parent specification #1; this slice adds only the behavior listed below. Keep app/lab labels and accessibility text English; localization may be added later. Use the same public interface in consumers and tests. Do not publish/deploy as part of implementation.

## Scope

- Add visual sequence/parallel/stagger/delay and curved-path recipes over already committed transactions; validate dependencies and reject cycles.
- Implement spawn/deal/reveal/dismiss/remove/copy lifecycle semantics, inert exit visuals, generation-safe re-addition and per-operation completion results.
- Add presentation cues driven by the scene clock, not business-state callbacks. Independent channels may continue while another is superseded.
- Bound presentation backlog with normal/accelerated/immediate modes; reduce decorative work before input responsiveness and preserve current desired state.

## Acceptance criteria

- [ ] Normal, accelerated, skipped and reduced-motion routes reach identical committed state.
- [ ] Removal releases logical membership/input immediately; re-add during exit reuses the correct shell and cancels stale cleanup.
- [ ] Sequence cancellation releases dependents without fake/late impact cues or unresolved handles.
- [ ] Input remains usable during a burst of deals/removals; reproduce with a deterministic clock.

## Runnable lab scenario

Deal ten cards in a stagger, reverse one move, remove/re-add another during exit, and accelerate then skip the remaining visuals.
